# HopKey

HopKey is an end-to-end encrypted vault for SSH hosts and keys. The `hop` CLI and a local daemon keep decrypted keys in memory and serve them to the OpenSSH client through an ssh-agent socket, so plain `ssh <alias>` works on every device. `hop-server` is the Docker server that syncs ciphertext between devices; it never sees a key or a host in plain form.

The repository holds both. Phase 1 is the local `hop` CLI and daemon with the encrypted vault, which works on its own with no server. Phase 2 adds `hop-server`, automatic sync in the daemon and the `hop auth` account commands. `hop mcp` gives local AI agents the hosts, under the rules below.

## The `hop` CLI

```
hop <target>                      shell on a vault host: alias, hostname, IP, Tailscale name or IP (user@ works)
hop exec <target> [--timeout D] [--sudo] [--json] -- <cmd...>
hop check|which|trust <target>    diagnose, explain resolution, pin the server's host key
hop ls [tag] | info <target> | add | edit | rm
hop key add <path> | ls | pub <key> [--fingerprint] | rm | rotate <key>|--all [--hosts h1,h2] [--type ed25519|ecdsa|rsa] [--new-key K] [--dry-run] [--yes] [--keep-old]
hop snippet add <name> [--description D] -- <cmd...> | ls | rm <name>
hop import ssh-config [path] [--with-keys] [--dry-run] [--yes]
hop ts import [--dry-run] | ts link <host> <node-id-or-dns-name>   (never links an ambiguous match; pick the node with ts link)
hop setup                         put `Include ~/.ssh/hop/config` above every other directive in ~/.ssh/config
hop init [--device-key-store keychain|file] [--kit-file F] [--json]
hop lock [--end-sessions] | unlock [--password] | passwd [--kit-file F]
hop status | daemon [stop [--json]]
hop sync [resolve]                sync now, settle a change the daemon held
hop auth signup|login|approve|status|devices|logout|rotate|passwd|merge|resume
hop mcp [--read-only] [--tag T]... | mcp install [--client claude|codex|print] [--read-only] [--tag T]... [--json]
```

`hop import ssh-config` reads your config with `ssh -G`, the way `ssh <host>` does, so it runs any `Match exec` commands in it and may do DNS lookups. It lists what its own scan found (best effort, not a guarantee) and asks before it runs ssh; without a terminal, or with `--json`, it refuses unless you pass `--yes`. Importing your config carries the same trust as using it.

`hop key pub <key>` prints a vault key's public half as an `authorized_keys` line (`ssh-ed25519 AAAA... <key name>`), and `--fingerprint` prints its `SHA256:` fingerprint, as `ssh-keygen -l` shows it; `--json` gives the id, name, type, line and fingerprint. It reads only what the daemon already lists for `hop key ls`: no private byte is read or printed.

Every command takes `--json`, except `hop <target>` (`hop connect`), which opens a shell, `hop daemon`, which runs in the foreground, `hop mcp` itself, which speaks MCP on stdin and stdout (`hop mcp install` takes it), and `hop passwd`, which prints the new Emergency Kit and so has no output that is safe to parse (on a server, `hop auth passwd --json` takes it, with the kit on stderr). A first word that is not a command, followed by more words, is refused as an unknown command, not taken as a target. hop's own failures exit 255, and `hop <target>` and `hop exec` pass the remote exit code through. `hop daemon` exits 75 when another hop process owns the vault: a command that started it then waits for that other daemon. Resolution is interactive (DNS, fuzzy match, picker, plain-ssh fallback) only when stdout is a terminal and `--json` is not given; otherwise it stops after the Tailscale step and returns candidates. `hop exec` is never fuzzy.

Routing never looks names up in DNS. A host goes over Tailscale when it is linked to a node (`hop ts import` or `hop ts link`) or one of its addresses is a Tailscale IP or an exact MagicDNS name. A bare name such as `build` stays a direct address even when a tailnet node has that host name, because it may be a LAN name, and a host behind a jump host is resolved by the bastion. `hop which`, `hop info`, `hop check` and `hop add` then say `build matches tailnet node build; to route over Tailscale: hop ts link <host> <node-id>` (the node's stable ID, which names it unambiguously) when exactly one node matches and the host has no stored link and no jump host. The hint is not shown to `hop mcp`.

`hop ts import --dry-run` prints `would create` and `would link`; its `--json` report has the statuses `would_created` and `would_linked`.

A host with no pinned host key is refused by ssh, since hop never trusts a key on first use. `hop <target>` and `hop exec` say so before they run ssh, and name the fix: `hop trust <host>`, or, for a host behind a jump host (whose key hop cannot read directly), `hop edit <host> --host-key '<ssh-ed25519 AAAA...>'`.

The first command that needs the daemon starts it (`hop daemon`, detached, logging to `$XDG_STATE_HOME/hop/daemon.log`; the daemon of the login service, `hop setup --service`, logs to the journal on Linux: `journalctl --user -u hopkey`). `hop status` does not start the daemon: it says so, and `hop daemon` (in the foreground) or any command such as `hop ls` starts it. The daemon serves the read-only ssh-agent socket and a control socket in `$XDG_RUNTIME_DIR/hop/` (or `~/.ssh/hop/run/`), and regenerates `~/.ssh/hop/config` after every change, so plain `ssh <alias>` works too. While the daemon is down or the vault is locked, the agent has no key to offer and plain `ssh <alias>` fails with `Permission denied (publickey)`; any hop command starts the daemon again, and `hop unlock` unlocks the vault.

## The vault

The vault lives in `$XDG_DATA_HOME/hop` (or `~/.local/share/hop`) as a signed log. The contents of vault items (hosts, keys, credentials, snippets) are encrypted on disk. The log's public metadata and the verified state are not encrypted and are not secret: account, device and item IDs, item types and versions, device names, public keys, sequence numbers, times and digests. `hop init` creates and opens the vault itself; after that the daemon is the one process that opens it, and every other command goes through the daemon.

- `hop init` creates the account and the vault. It asks for a master password and prints the Emergency Kit: the Secret Key and the Recovery Key. You type back the last group of each before anything is written. `--kit-file` also saves the kit to a new 0600 file. It needs a terminal (stdin) for the password and the type-back, so it refuses to run without one. With `--json`, stdout holds one JSON result (the data directory, the device key store, the kit file if any, and no secret) and the kit and the prompts stay on the terminal, on stderr.
- `hop lock` drops every secret from memory and empties the agent. ssh sessions already open keep running; `hop lock --end-sessions` also ends the ones hop started, as a revocation does (see "Open sessions" below). `hop unlock` opens the vault again with the device key. `hop unlock --password` uses the master password and Secret Key instead and sets up a new device key, for when the old one is gone. The old device stays in the log as stale until the next `hop passwd`.
- `hop passwd` changes the master password. That re-keys the whole vault and makes a new Secret Key and Recovery Key, so keep the new kit. It also revokes the stale devices that password unlocks left behind.
- The device key record (this device's private keys and the Secret Key) is kept in the OS keychain by default. On a machine without one, `hop init --device-key-store file` keeps it in `device.key` next to the vault, sealed with a passphrase when `HOP_DEVICE_PASSPHRASE` is set. Every unlock after that needs the passphrase. A daemon started with `HOP_DEVICE_PASSPHRASE` in its environment uses it. One started without it (by `hop mcp`, or by the login service) comes up locked, and `hop unlock` opens it: it sends the daemon the passphrase from its own `HOP_DEVICE_PASSPHRASE`, or asks for it on a terminal. The daemon uses it for that unlock only and does not keep it, so after `hop lock` the next `hop unlock` needs it again. Without the passphrase the file is unsealed: it holds the device private keys and the Secret Key in plain form, protected only by its 0600 file permissions, and `hop init` warns about that. hop never falls back from one store to the other. `hop status` shows the store in use, `keychain`, `file (sealed)` or `file (unsealed: private keys on disk)`, and warns about anything pending.

For development, build with `-tags hopdev`: the vault is then a plaintext JSON file (`$HOPKEY_DEVSTORE`, default `~/.local/state/hop/devstore.json`) that holds private keys unencrypted. A test checks that a normal build contains none of that code.

## Sync

Once a vault is signed in to a server (`hop auth signup` or `hop auth login`), the daemon keeps it in sync on its own: it pushes each change as it is made and holds a long-poll open for the other devices' changes. A change made offline is queued (`pending` in `hop ls`) and goes up once the server answers again. `hop status` and `hop sync` show where sync stands: `online` once the server has answered, `retrying` with the last error and the next try when a pull or a push failed (a push, in the background or by `hop sync`, gives up after 15 seconds), and `paused` while the vault is locked. `hop setup --service` runs the daemon from login, so sync goes on with no hop command run. On a device whose key is a sealed file, that daemon has no passphrase: it starts locked after every boot, and sync is paused until `hop unlock`. Setup warns about this. hop writes the passphrase to no file, so for a service that unlocks by itself keep the device key in the keychain or an unsealed file.

When two devices change the same item before either sees the other's change, the merge goes by field:

- Fields that only make sense together form a unit, and two different changes to one unit are held: the change that reaches the server second waits in `hop sync resolve`. A host has three units: how it connects (addresses, port, user, route, Tailscale link, pinned keys, jump host, key and credential), its name, and what agents may do on it (agent access and agent output together). A snippet's name, command and parameters are one unit, and so is everything in a key, a credential or a policy, so two changes to any of those are held as before.
- A host's tags and aliases merge as sets: a tag one device added and another device removed both apply. Spellings that select the same thing are one tag or alias (`prod` and `Prod` for a tag, `db` and `db.` for an alias), and if the two devices changed one of them differently, for example one removed `prod` while the other respelled it `Prod`, the change is held.
- Some changes are held even though they touch different units, because together they would apply one device's intent to a machine the other device never saw: a new name, alias or tag on one device while the other changed how the host connects, and agent access widened (allowed, or more of the output) on one device while the other changed how it connects. Removing a tag or narrowing agent access merges with anything.
- Otherwise the two changes are combined, each field keeping the change made to it. The device that combined them says so in `hop status`, `hop sync` and its daemon log, naming the item and the fields each device changed (never the values), until its daemon restarts; the vault keeps the note, sealed, until the daemon has shown it (the newest 50; older ones are counted as dropped). A field this hop doesn't know (from a newer hop) makes the whole item follow the earlier rule: any two changes to fields other than the description are held.
- `hop sync resolve` shows what holds a change: the unit, the tag or alias, or the coupling and which device's change set it off. Keep mine, edit and take theirs do what they always did. When only some fields conflict, `--keep-mine --merge` and `--take-theirs --merge` settle those fields your way or the server's and keep everything else merged; each prints its proposal and needs `--confirm` with its token, like keep mine. A change too large for the server once merged (over 1 MiB for one item, or 4 MiB for the whole change) is held before it is sent, with a reason that names the size; edit it or take theirs.
- The description is merged on its own, and the last change to reach the server wins. Nothing is held, so the other device's description is lost. The device whose change won says so in `hop status`, `hop sync` and its daemon log, naming the item and the field (never the values), until its daemon restarts. It does so even when the server's answer to its push was lost and a later sync, or a `hop auth` command run meanwhile, found the change committed: the vault keeps the note, sealed, until the daemon has shown it (the newest 50; older ones are dropped with a line in the daemon log).

`hop auth devices` shows, under LAST SEEN, when each device last wrote to the vault or made any request to the server, whichever is later. The server records a device's requests at most once a minute.

`hop auth login` by approval waits for a signed-in device to run `hop auth approve CODE`. An approving device allows 3 approvals per rolling hour; when it has used them, its error says when the next one frees up, and the new device, which cannot see that, prints a hint after a minute: cancel the login (Ctrl-C), run `hop auth login --discard`, then sign in with `--method password`. An unfinished approval login on a device makes the other methods refuse to start; `hop auth login --discard` (with `--yes` or a question) deletes it, and the approving device's `hop auth approve --abort` ends its side. `hop auth login` and `hop auth approve` stop, and release the vault, on SIGHUP (unless it was ignored when hop started, as under `nohup`) and when the terminal they run in goes away.

`hop auth logout` deletes this device's keys and its copy of the vault, and with them what the vault decrypted into `~/.ssh/hop`: the config is left with no hosts (so an `Include` of it still works), and the key files and pinned host keys there are removed. A revoked device's daemon does the same. hop removes only the names it generates there (`keys/<id>.pub`, `known_hosts-<id>`, where `<id>` is 16 hex digits, and its own temp files), so a file of yours in `~/.ssh/hop`, such as `keys/company.pub`, stays. It leaves your own `~/.ssh/config`, `~/.ssh/known_hosts` and key files alone. If a logout is cut short after it was recorded (a crash, say), the next hop command finishes it, `~/.ssh/hop` included, and if `~/.ssh/hop` cannot be emptied then, every later start of the daemon tries again until it can.

## What revocation does

`hop auth devices revoke <device>`, run on another device, removes a device from the account. The server stops serving it at once, and the vault's keys are replaced (a new vault key, Secret Key and Recovery Key), so nothing written after the revocation can be read with what the revoked device holds. What happens on the revoked device itself depends on whether it can reach the server, and on whether it can prove the revocation. This applies only to a device signed in to an account; a local-only vault has nothing to revoke.

- **Online.** The revoked device notices within seconds: the server refuses it a session. Its daemon empties the agent and the ssh config in `~/.ssh/hop`, and locks the vault.
- **Proven.** The daemon then asks the server for the entries from its own last verified head up to the one that removed it, without their contents. Each must chain from the one before and carry the signatures the device can check against keys it already trusts, through every change of the account key and of the account's devices on the way (a revocation is signed by another device of the account and by the account key). What that proves is an authenticated departure authorization: the signatures and the membership changes are verified, the vault contents those entries carry are not. If it verifies, the revocation is the account's, not just the server's word, and the device wipes itself as `hop auth logout` does: its copy of the vault, its device key and the files hop wrote to `~/.ssh/hop`. It keeps one small record, so `hop auth status` can say what happened. `hop auth login` signs in again as a new device. Status says "verified" as soon as the proof verifies, and "wiped" only once the files in `~/.ssh/hop` are gone too; a wipe cut short (a crash, say) finishes at the next start.
- **Unverified.** If the proof can't be had or doesn't verify (an older server, say), the device records the server's report on disk and stays locked: `hop unlock`, `hop unlock --password` and every daemon start refuse, and nothing is deleted. `hop auth logout` wipes the device; `hop auth login` signs in again. The report clears only if the server authenticates the device again, which an honest server never does for a revoked one; on a device whose key file is sealed, `hop unlock` asks for the device passphrase to let the server check it. A server that lies can lock a device out (it could refuse it anyway), but it can't delete anything on it. The record carries a MAC under a key only this device holds, so tampered details are not shown as the server's: `hop auth status` calls such a record corrupt, and it keeps the vault locked all the same. The MAC protects nothing else. Whoever controls the device can still delete the record, as they can delete the whole vault.
- **Refused without a report.** If the server refuses the device a session without saying it left, or answers in a way hop can't use, the vault stays locked and nothing is recorded or deleted; `hop status` says why, and the next `hop unlock` or sync asks again. That includes a server whose operator disabled the account or blocked the device (see Running hop-server): the daemon locks the same way when a pull, a push or a session renewal is refused, not only at start and unlock.
- **Offline.** A device that can't reach the server doesn't know it was revoked, and keeps working until it reaches the server. Before the daemon loads any key, at start and at each `hop unlock`, it asks the server whether the device is still in the account, for up to about 3 seconds, a sync in progress included (a long-poll is cut short for it). If the server can't be reached in that time (no network, a name that doesn't resolve, a connection refused or reset, a timeout, a TLS certificate that doesn't verify, as behind a captive portal, or a server or proxy that answers it is down or busy), the keys load anyway, so hop keeps working offline, and `hop status` says the check was skipped. Any other answer keeps the keys out (see above).
- **Max offline.** `hop auth policy --max-offline 7d` (any duration from a minute to ten years, or `off`, which is the default) is an account setting that syncs to every device: a device that has had no answer from the server for longer locks, and refuses to unlock with "offline too long; connect to the server" until it reaches the server again. A last contact more than 5 minutes in the future counts as too long: the clock was set back. That is the clock skew the policy allows. Every answer from the server counts as a contact, so a device that stays online never locks, however short the policy; after a restart, the daemon counts from the last contact it wrote down, which may be up to a minute earlier. `hop auth policy` shows the setting. This limits how long a lost device that stays offline keeps working, but someone who controls the device can defeat it (by editing its files or its clock); only rotating the keys helps against that.
- **Open sessions** that hop started end within seconds of the device learning it was revoked (any of the cases above where the server refuses it a session or reports it gone, at a daemon start too), and of the max-offline lock: `hop <target>`, `hop exec`, `hop check`, `hop mcp`'s `exec` and `run_snippet`, and `hop key rotate`. Each of these hop processes runs ssh as its own child and listens to the daemon while ssh runs; when the daemon says the device was revoked or locked, the hop process sends its ssh SIGHUP, then SIGTERM after 2 seconds and SIGKILL after 5 if it still runs, and says "the hop daemon ended this ssh session when this device was revoked" (or why it ended). The daemon signals no process itself. A session hop starts after that, until the vault opens again, is ended as it starts. `hop status` and `hop auth status` count the termination requests the daemon sent to those hop processes ("4 termination requests sent to ssh sessions hop started, when this device was revoked"), not ends it saw happen; in `hop status --json` and `hop auth status --json` the count is `ended_sessions.termination_requests` (it was `ended_sessions.count` before).
  - *Suspended sessions:* a `hop <host>` suspended (ssh's `~` Ctrl-Z escape, or Ctrl-Z before the session is up) is stopped, with its ssh, and acts on a revocation when it is resumed (`fg` or `bg`): it then ends its ssh at once. Until then the session stays open, stopped, and counts among the termination requests sent.
  - *Hangups:* `hop <host>` passes SIGHUP and SIGTERM on to its ssh. Started with SIGHUP ignored (under `nohup`, say), it leaves it ignored, and its ssh starts with it ignored too, as a plain ssh would.
  - *Not ended:* plain `ssh <alias>`, `scp`, `sftp`, `rsync` or `git` over ssh to a hop alias, through hop's `Include` or `-F ~/.ssh/hop/config`: hop did not start them, and does not look for them. Connect with `hop <host>` for sessions that a revocation ends.
  - *Offline devices* keep their sessions, and hop keeps working, until they reach the server and learn of the revocation, or until the max-offline policy locks them. For a stolen device, rotate the keys (below).
  - *Without the daemon:* a session whose hop process can't reach the daemon (it was not running, or was stopped or restarted) runs as before; the hop process tries again every 5 seconds while the session lasts, and `HOP_DEBUG=1` makes it say so on stderr.
  - *A plain `hop lock`* leaves sessions alone; `hop lock --end-sessions` ends the ones open then, the way a revocation does.
- **SSH keys stay valid until rotated.** The vault's private keys are re-encrypted, not replaced, and your hosts still trust their public keys. Anything the revoked device copied while it was a member still logs in. To cut that off, rotate the keys (`hop key rotate`) or remove them from `authorized_keys` on your hosts.
- **Your own key files stay.** Files you imported with `hop key add` are yours: hop never deletes them, on a revoked device or anywhere else.

## Rotating keys

`hop key rotate <key>` replaces an SSH key on every host that uses it, over the access hop still has. `--all` does it for every key in the vault, and `--hosts h1,h2` limits it to those hosts. It is the step that actually locks out a lost, stolen or tampered device. Revoking the device stops it from syncing, but it may have kept a copy of every key it could decrypt, so `hop auth devices revoke` ends by naming those keys and offering to run `hop key rotate --all` (with `--json`, its report has a `rotate_command` field instead).

hop shows the plan first: the new key (`<name>-rotated-<date>`, of the old key's type unless `--type` says otherwise), the hosts it will change, and the hosts it skips with the reason. A host is skipped when hop cannot log in to it safely: no pinned host key, a jump host that is missing or unpinned, a password-only host, or a host reached through Tailscale SSH, which does not use the key. `agent_access: deny` does not stop it, since you run it, not an agent. `--dry-run` stops after the plan. Without a terminal, hop refuses unless you pass `--yes`.

The new key goes into the vault first. Then, one host at a time:

1. hop logs in with the old key the usual way (pinned host key, jump hosts) and reads `~/.ssh/authorized_keys`.
2. For each line that holds the old key, hop adds the new key with the same options (`from=`, `command=`, `restrict` and so on, read with sshd's quoting rules) and the comment `hop-rotated <date>`. It never adds a line that is already there. Each edit is one script on the host: it takes a lock in `~/.ssh` that other hop runs wait for (see below), checks that the file is still byte for byte what hop read, writes a temp file in `~/.ssh` that copies the old file's mode and owner, checks the file again, and renames the temp file over it. Any mismatch stops the edit with nothing changed.
3. hop logs in again on a new connection that offers only the new key: an ssh config of its own (none of hop's generated config, none of yours), with the host's pinned keys, the same address, port and user, the jump host reached through hop's config, and an agent that holds the new key and nothing else.
4. Only then does it remove the old key's lines, matched by the key itself, and no other line. It checks that the old key is now refused, the same way with the old key alone, then points the host at the new key in the vault. The old key counts as refused only when ssh's own debug log of that login, kept apart from the jump host's output, shows all of it: the connection reached the host itself, ssh offered the old key, the server never accepted it, and the server ended the login with `Permission denied (publickey)`. A jump host that turns the key away, a key hop could not offer or sign with, or a server that accepts the key does not count: the host is then pointed at the new key but reported as `needs-attention`, with what hop saw, and the old key stays in the vault. Pointing the host at the new key is one conditional write: the vault makes it only while the host's record, and the record of every jump host on the way to it, still hold what hop tested (their versions and connection details, checked in the same transaction as the write, so a sync already received cannot slip in between). That check covers this device's copy of the vault when the change is saved. A jump host edited on another device that this device has not received yet is not part of it: the host's own record is guarded when the change reaches the server, but a jump host is a separate record, so its edit and the repoint can both go through. The key is installed on the host either way, but a `from=` option copied from the old line may name the old jump host's address, so check such a host after a rotation if someone was editing its jump hosts at the same time. If one changed meanwhile (an edit on another device, say), hop reads them again and tries once more only when everything that decides where ssh connects is as it checked it: the address, port, user, route, Tailscale link and pinned keys of the host and of each jump host. If the write's answer is lost, hop reads the record back, and a record that already names the new key, and still reaches the server hop checked, counts as done.

If any step fails, hop puts that host's `authorized_keys` back as it was: the added lines go and the old ones stay. The host is reported as failed and keeps the old key in the vault. If hop cannot put it back, or cannot tell what the host takes (the connection dropped during an edit, so hop does not know whether it went through), or the host's record changed under it, the host is reported as `needs-attention`: both keys stay in the vault, and the report says what hop knows of the host and names the command that finishes it, `hop key rotate <old> --hosts <host> --new-key <new>`. That run reuses the new key, reads the host with whichever key logs in, and carries on from where the host is. `--new-key` also takes a host that already points at the new key: then hop only removes the old key's lines and checks that the old key is refused. When the record itself moved (another address, another Tailscale node, other jump hosts), the report says where the server hop changed stands and what the record names now, and names the command only when it fits that record; a record that was deleted, or that now uses neither key, has none.

A host whose old key does not log in but whose new key does (a second record for an account rotated first through another, or an earlier run that got that far) is finished over the new key alone: hop reads `authorized_keys` with it, removes any line of the old key still there with the same guarded edit, checks that the old key is refused, and points the host at the new key. It is reported as `already-rotated` only when the old key is shown to be refused. Otherwise it needs attention, and the old key stays in the vault.

The new key is deleted from the vault again only when every host hop started on is known to be as it was. The old key is deleted only when no host uses it any more and no host needs attention, and never with `--keep-old`. The changes sync like any other edit. hop prints one row per host (`rotated`, `already-rotated`, `failed`, `needs-attention` or `skipped`, with the reason; `--json` gives the same, with the host's `remote_state` and the `fix` command) and exits non-zero if a host failed or needs attention.

Ctrl-C during a rotation, also one started from `hop auth devices revoke`, does not stop hop in the middle of a host: it finishes or puts back the host it is on, skips the rest, and keeps the keys as above.

The new private key is made in the hop process. It goes to the daemon the way `hop key add` sends a key, and to ssh only through that one-key agent, on a socket in hop's private run directory, for as long as the command runs. The check of the old key uses the daemon's agent through a filter that offers that one key. No private key is written to disk.

Limits:

- The lock is the directory `~/.ssh/.hop-authorized_keys.lock.d`, made with `mkdir`, the same way by every hop run whatever the host has installed. `hop key rotate` and `hop access` both use it. The file `owner` in it holds a random token of the run that holds it, the PID of its shell on the machine that took it, and the time it took the lock. A run removes the lock on the way out only if it still holds its own token, and only after it has removed its own working directory, `~/.ssh/.hop-s.<token>`; if it can't confirm either, it says so and leaves the lock in place (exit status 89, and the host needs attention). hop never takes over a lock, however old: a script on the server can outlive the ssh that started it, and the PID may belong to another machine that shares the home directory. If the directory is there for more than ten seconds, the edit stops with nothing changed (exit status 85), and the message names the directory and the owner's PID and time. Remove it yourself (`rm -r ~/.ssh/.hop-authorized_keys.lock.d`) only when no `hop key rotate` and no `hop access` run can still be active for that account, on any of your devices and on any machine that shares that home directory. If you remove it while one is active, run `hop access check` afterwards.
- The lock keeps other hop runs out, but nothing else respects it: an editor, configuration management or another tool that writes `authorized_keys` between hop's last check and its rename (a few milliseconds) has its change replaced.
- The edit script is tested on Linux, with `dash` and `bash` as `sh` and as the login shell. Other shells are untested: busybox `ash`, the `sh` of FreeBSD and macOS, and `zsh`, `fish` or `tcsh` as the login shell. It is written to POSIX `sh` and sent so that those login shells should pass it through unchanged, but hop does not claim them.
- The host needs a POSIX `sh`, `cksum`, `cp -p`, `mv`, `ln`, `mkdir`, `rmdir` and `date`, as the rest of hop needs a POSIX shell, and a filesystem for `~/.ssh` that supports hard links (hop refuses to edit otherwise, rather than risk a copy that isn't atomic). hop edits only `~/.ssh/authorized_keys`. If the server reads keys from somewhere else (`AuthorizedKeysFile`, `authorized_keys2`, a forced `command=` on the old key's line), hop finds the old key missing, or sees the new key fail to log in, and changes nothing. If the server still accepts the old key after the rotation, from another file, the host needs attention, and you need to remove the key from that other place yourself.
- `hop key rotate` and `hop access` write the new `authorized_keys` in a working directory inside `~/.ssh` and then rename it into place. Before they write anything, they hard-link the new file into `~/.ssh` as a test. If the filesystem doesn't allow that (AFS, for one, allows hard links only within one directory), the edit stops with nothing changed (exit status 84) and says: hop's temporary file can't be hard-linked into ~/.ssh, so hop can't be sure that replacing ~/.ssh/authorized_keys would be a rename; nothing changed. hop has no other way to write the file there. If `mv` itself fails, hop can't tell whether the file was replaced, and the host needs attention.
- Lines that carry a `hop-access:` marker in their comment, and `# hop-access-removed` comment lines, belong to `hop access`. Rotate never copies, removes or restores them, byte for byte. If the old key's only lines carry a marker, rotate changes nothing; if one still holds the old key after the rotation, the host needs attention and the old key stays in the vault.
- A symlinked `authorized_keys` is not edited. hop does not edit system files or keys trusted as a `cert-authority`. On SELinux hosts, hop runs `restorecon` on the new file when it is there. A file managed by configuration management (Ansible, Puppet, cloud-init) may be rewritten with the old key the next time that tool runs. Change it there too.
- hop rotates only keys in the vault, on hosts in the vault. Key files of your own on other machines (the file you once ran `hop key add` on, say) are not touched. Delete them yourself if the old key should be gone everywhere.
- A token grant's dedicated key is not rotated. Reissue the grant instead.
- `hop mcp` does not offer this to agents.

## Giving a colleague access (`hop access`)

`hop access add LABEL HOST... --pubkey "KEY" --fingerprint SHA256:...` puts a colleague's public key on your hosts as a line hop manages: the key, the options you chose (`--from CIDR,...`, `--restrict` or `--no-forwarding`; none by default, which is a full login with forwarding), and a comment `hop-access:<record id>`. The record, with the key and each host's state, is kept encrypted in the vault; hop mcp never shows it. The fingerprint must reach you over a different channel from the key, or it proves nothing. A host needs a pinned host key (`hop trust HOST`): each host's line is bound to the key the host presented when it was added, and every later connection for it accepts only that key. If the host's pins change, `hop access migrate LABEL HOST` moves the record to the new key, or `hop access rm LABEL --abandon HOST` gives up on it.

`hop access ls` lists the records and what hop last recorded for each host, and never connects. `hop access rm LABEL [HOST...]` removes the lines; `hop access forget LABEL` deletes a record whose hosts are all removed or abandoned. `hop access check [LABEL] [--host HOST] [--all-hosts]` reads every host your records name, removed and abandoned ones included, and tells you what to fix; it takes no lock and changes nothing. Its exit status is 0 when it found nothing but information, 1 when it found something to fix, and 2 when it couldn't read a host.

- What removal does. `hop access rm` removes the line hop added to the host's `~/.ssh/authorized_keys` and, in the same step, adds a comment line, `# hop-access-removed <record id> <number>`. hop never adds that record's line to that file again while the comment is there. hop doesn't remove these comment lines; you may, but then that protection is gone for that record on that host. At 128 of them in one file, `hop access rm` can't remove new records there.
- What hop promises. If you use hop access from one device at a time for a host, and your server is working normally, every line hop added is one of your records (except a line you let hop leave with `--abandon` and whose record you then forgot), and a line you removed stays removed. If two devices change the same host at once, if someone removes hop's lock by hand, if a hop run is killed, or if the server misbehaves, hop may leave a line no record names or show a state that is out of date. Run `hop access check`: it reads every host your records name and tells you what to fix.
- Crashes and restores. If the host loses power or crashes within seconds of `hop access rm`, the change may not have reached its disk, and the line can come back when it restarts. If the host, or its disk, is later restored from a snapshot or backup taken before the removal, the line comes back with it. hop won't notice by itself; `hop access check` finds it while the record still exists, or with `--all-hosts` afterwards.
- What the comment line shows. The comment line stays after the access is gone. Anyone who can read that file sees the record's ID, which was already on the removed line, and a number that counts hop's steps on that host. The same record ID on several hosts shows that one record covered all of them. It doesn't name the person, the key or your label.
- Shared host keys. If two of your host records pin the same host key, hop can't tell whether they are one machine. `hop access rm` then asks you: use `--same-machine` if they reach the same machine and the same account, and hop records the removal of that target as done on your word; use `--abandon` if not, and hop records that the line may remain. `hop access check` reads the file through each of those host records and tells you if they differ.
- Abandon, then forget. `hop access rm --abandon` leaves the line on that host, and `hop access forget` then deletes the record. After that the line belongs to no record of yours: `hop access check` reports it as an untracked line every time it runs, until you delete it from that host's `~/.ssh/authorized_keys`.
- A held lock. hop access and `hop key rotate` share the lock described under rotation, with the same advice: remove it only when no hop run can still be active for that account, on any device or machine that shares the home directory, and run `hop access check` afterwards.
- What hop can't see: other `AuthorizedKeysFile` paths and other login users, `AuthorizedKeysCommand`, certificates from a CA the host trusts, passwords, and keys the colleague added while logged in. Removal doesn't end open sessions or multiplexed control connections. Machines cloned with the same host key aren't told apart.
- `hop access add` doesn't add a host whose `~/.ssh/authorized_keys` is a symbolic link, doesn't exist, or is larger than 1 MiB: nothing is recorded for it, and the run says why. Create the file first. If the file becomes a link or goes missing later, the add fails there, and a removal stays unfinished with the advice of what to do.
- Right before each connection to a host, hop checks the key a target is bound to against that host's pins as the vault holds them then, so a pin another device removed, even one a sync brought in during the run, stops that host with nothing changed. Once the host has started sending its file under the lock, it has 30 seconds to send it and take hop's change; after that hop gives up with nothing written, and ends the connection a few seconds later if the host hasn't.
- Labels are unique among your records, compared without case and without a trailing dot. A run names the record it started with until it ends, even if another device removes it and makes a new record with the same label meanwhile.
- Revoking a device revokes no colleague. `hop access ls` marks a record last changed by a revoked or retired device. After a checkpoint that revokes a device which last changed some records, `hop status` shows a note naming them, after every restart, until `hop access ls` has shown it. The note is a snapshot of that checkpoint: if a device you still use changes one of those records later, the note still names it, and `hop access ls` no longer marks it.
- What is tested: Linux hosts, `dash` and `bash` as the host's `sh` for the session script, and OpenSSH 9.2p1 as the client whose log names the host key a target is bound to. Other OpenSSH versions, other operating systems (macOS, the BSDs), busybox `ash`, and `zsh`, `fish` or `tcsh` as the login shell are untested. hop is written for them; with an OpenSSH that logs the host key differently, `hop access add` refuses the host rather than guess.
- A server must accept access records (hop-server from this version on); hop checks before it writes one. Devices running an older hop stop syncing once the vault has an access record, and those that already synced it can't unlock the vault until upgraded.

## Using hop with AI agents (MCP)

`hop mcp` is an MCP server on stdin and stdout for local agents such as Claude Code and Codex. It is a thin layer over the daemon, like every other command: it never opens the vault, and works the same on a local-only vault and a signed-in one. If the vault is locked or missing, a tool says so and names the fix (`hop unlock`, `hop init`); the server keeps running. If no daemon is running, `hop mcp` starts one, without `HOP_DEVICE_PASSPHRASE`: on a device whose key file is sealed with a passphrase, that daemon comes up locked, and the tools say to run `hop unlock` from a terminal, which sends the daemon the passphrase.

Register it once with the client's own CLI:

```
hop mcp install --client claude          # runs: claude mcp add --scope user hop -- /path/to/hop mcp
hop mcp install --client codex           # runs: codex mcp add hop -- /path/to/hop mcp
hop mcp install --client claude --read-only
hop mcp install --client claude --tag work --tag lab   # runs: ... hop mcp --tag work --tag lab
hop mcp install                          # prints the commands, the JSON (mcpServers) and Codex TOML to paste
```

hop never edits a client's config file itself. If the client already has a server named `hop`, remove it first (`claude mcp remove --scope user hop`, `codex mcp remove hop`).

Tools:

| Tool | What it does |
| --- | --- |
| `list_hosts(query?, tag?)` | Hosts: name, aliases, addresses, user, port, tags, description, auth (`key`, `credential` or `agent-only`), Tailscale status, whether a host key is pinned. |
| `resolve_host(target)` | One host, or candidates, as `hop which --json`. Nothing is guessed. |
| `exec(hosts, command, timeout_s=60)` | Runs a command on one host, a list, or `tag:x`, eight at a time. Per host: `exit_code`, `stdout` and `stderr` (the last 64 KiB each), `truncated`, `error` when hop could not run it, and `warning` when the output may be incomplete (ssh exited but left a process holding its output, which hop cuts off after a second; `truncated` is set too). `hop exec --json` has the same fields, and without `--json` hop prints the warning on stderr. |
| `check_host(host)` | The step-by-step diagnosis of `hop check`. |
| `ssh_command(host)` | The `ssh -F ...` command line for an agent that has its own shell. |
| `list_snippets()` | Saved commands and their `{{name}}` parameters. |
| `run_snippet(name, hosts, params)` | Runs a snippet as `exec` does. Each value arrives as one word and never becomes shell source text (see below for what that does not cover); a missing or unknown parameter is refused. The answer names the snippet; it does not show the command with the values filled in. |

Commands run with no terminal, stdin closed, `PAGER=cat` and a timeout per host, so a password prompt fails instead of hanging. Use `sudo -n`. One host failing does not stop the others. `exec` and `run_snippet` hand the command to the remote user's login shell, which must be POSIX `sh` compatible (sh, bash, dash, ksh, zsh). fish and csh quote differently, and are not supported.

Snippets are saved with `hop snippet add restart --description "restart a unit" -- systemctl restart {{unit}}`. One word after `--` is a shell command line, as with ssh; several words are quoted one by one. Snippets sync like hosts.

A parameter's name is letters, digits and `_`, not starting with a digit. hop puts each value in a shell variable at the top of the script and the placeholder becomes a reference to it, so `systemctl restart {{unit}}` runs as `HOP_P_unit='...'; systemctl restart "${HOP_P_unit}"`. Param values never become shell source text: not in a word, a comment, a here-document or `$(...)`, whatever quotes, newlines or `$` they hold. A template that itself evaluates a value (eval, sh -c, arithmetic, indirect expansion) can still run it, and the snippet's author is responsible for that. Write a placeholder bare, outside quotes: hop refuses `'{{x}}'`, which would not expand, and `"{{x}}"`, which would nest the quotes. In a here-document body the variable's double quotes are printed with the value; to avoid them, write `$(printf '%s' {{x}})` there instead of `{{x}}`.

hop also refuses, when a snippet is saved and again when it runs, a placeholder in the places where a shell evaluates text, since a value such as `a[$(cmd)]` runs `cmd` there in bash:

- inside `$((...))`, `((...))`, `$[...]` or `${...}` (an array index or offset is arithmetic);
- inside `[[ ... ]]` (its `-eq`, `-lt` and the like are arithmetic); use `[ ... ]`;
- each of these to its end, over line breaks too;
- as an argument of `eval`, `let` or `trap`;
- as the command string of `sh -c`, `bash -c`, `zsh -c`, `dash -c`, `ksh -c` or `su -c`; pass the value as a positional parameter instead: `sh -c '... "$1"' sh {{x}}`;
- in an assignment, `v={{x}}`, `a[{{x}}]=1`, `export v={{x}}`, and in `$(...)` whose output is assigned (`v=$(... {{x}})`), since a variable can be evaluated later with `${!v}`, a nameref or arithmetic. To put a value in a command's environment, use `env NAME={{x}} command`.

This check is best effort: it is a lint, not a shell parser. It misses evaluation it does not know (`ssh other-host {{x}}`, `xargs sh -c`, a value piped to a shell, or saved by `for` or `read` and evaluated later), and may refuse a placeholder that only looks like one of these (`echo eval {{x}}`).

Migrating snippets saved before this version: a parameter name with a `-` (`{{a-b}}`) is now refused, so rename such parameters to use `_` (`{{a_b}}`); a snippet that assigns a value (`v={{x}}`, the old here-document advice) or uses one of the places above is refused when it runs. Re-save it with `hop snippet add` in the new form.

A snippet's command is shown to agents by `list_snippets`, so keep secrets out of it: pass one as a parameter instead.

Safety rules:

- hop never returns the vault's secret fields: private keys, credential passwords, the Secret Key, auth values. The daemon never sends them to `hop mcp`.
- Command output (`stdout`, `stderr`, and what `check_host` quotes from the network: ssh's messages in its login step and a server's message when hop reads its host key, in `--read-only` too) is what the remote printed, filtered for agents only. What you run yourself (`hop exec`, `hop <target>`, `ssh`, `hop check`) is never filtered: you always see everything. For agents, each host's `agent_output` setting decides:
  - `redacted`, the default, replaces four things. Private key blocks. The values of the hop auth secrets and `HOP_DEVICE_PASSPHRASE` that `hop mcp` started with. The vault's secrets. Well-known secret formats.
  - `full` replaces the same, but skips the well-known formats. hop's own and the vault's secrets are replaced even here.
  - `none` returns no output at all. The agent gets the exit code, the byte and line counts of stdout and stderr, whether the output was truncated, and a note that the host's policy withholds it. `check_host` keeps its step names, pass or fail and hop's own words, and withholds what the server or ssh said.

  Set it with `hop add` or `hop edit <host> --agent-output redacted|full|none`. `hop info` shows it, and `list_hosts` and `resolve_host` show it to the agent. It is a vault field and syncs like the rest of the host. `run_snippet` and `exec` on several hosts apply each host's own setting.
- The vault's secrets are found by the daemon, which holds the unlocked vault. They are each credential's password, each key's private half (whole, and each line of its body), the account Secret Key in the forms it may be printed in (as on the kit, in lowercase, without hyphens, and its secret part alone), a Recovery Key not yet confirmed, and the account's private keys, the vault key and this device's own key material (each in base64url, base64 and hex). A change still queued for the server does not drop the secret it replaces: until the server takes it, both the old and the new password are redacted. `hop mcp` sends the daemon the output, and the daemon answers where the secrets stand. Their values never leave the daemon. If the daemon cannot check the output (the vault was locked meanwhile, say), the output is withheld.
- The daemon rations these checks: at most 256 KiB a request, about 8 MiB a minute after a 1 MiB burst, and four at a time. Past that it refuses for a few seconds, and the output is withheld with the note "the hop daemon's redaction budget is exhausted; try again shortly". The check tells whether text holds a vault secret, so this bounds how fast a process can test guesses through it. It is a throughput limit, not a security boundary: a process running as you can read the unlocked vault through the daemon in other ways.
- Each stream keeps at most its last 64 KiB. hop reads the last 128 KiB, checks all of it, and only then cuts: a secret the cut would split goes whole, and the cut moves past it. A marker can be longer than the secret it replaces, so the limit is applied to what is returned, cutting only between whole markers and whole characters, and `truncated` says so. A cut keeps 1 KiB less than the limit, and where it falls inside a line, the rest of that line goes too, so what the agent gets does not begin in the middle of a line, unless that line is the last one (no newline follows it), which is then kept from the cut on. `check_host` reads 128 KiB of ssh's stderr from its login the same way.
- The well-known formats are AWS access key IDs and secret access key lines, GitHub (`ghp_`, `gho_`, `ghu_`, `ghs_`, `ghr_`, `github_pat_`), GitLab (`glpat-`), Slack (`xox[abprs]-`), Stripe (`sk_live_`, `rk_live_`) and Google (`AIza`) tokens, JWTs, `Authorization:` header credentials, a URL's password (`scheme://user:password@`), and the value of a key whose name says it is secret (`password`, `passwd`, `passphrase`, `secret`, `token`, `api_key`, `apikey`, `access_key`, `private_key`) in `KEY=value`, `key: value` and JSON `"key": "value"` forms. A key such as `password_file` or `token_type`, about a secret rather than holding one, is left alone. Random-looking strings are not guessed at: a checksum, a commit or an ID looks the same as a key.
- A secret becomes `[redacted by hop: <kind>]`, for example `[redacted by hop: github-token]`. Private key blocks become `[private key [redacted by hop]]`, and hop's own values `[redacted by hop]`. Every secret and format is found in the whole text before any is replaced, and before hidden names are masked. So none breaks up another, overlapping matches go as one, and a secret that runs into a key block goes whole. Under `redacted`, the well-known formats are looked for once more in the text as returned, where a marker or the cut now stands beside them: a token that a secret of hop's ran into is replaced once that secret is a marker. Under every policy, a denied host's name that the cut or a marker leaves standing on its own is hidden too. In `check_host`, where hop's own words meet the server's text, the two are checked together, and a secret that runs across goes from the start of the server's text. Each result counts by kind the markers it returns; one the 64 KiB limit cut off is not counted. A server's disconnect message, which the SSH library quotes in its error, is checked as the server sent it, so a secret with a `"` or a `\` in it is found; a message hop cannot unquote is withheld. hop mcp's own stderr, which the MCP client keeps in its log, is scrubbed of its own values and key blocks.
- Every value hop holds is replaced however short, so a short password also masks the same text where it is not a secret.
- Snippet commands are shown to agents as they are; keep secrets out of them.
- A host with `agent_access: deny` is invisible to every tool: not listed, never resolved or offered as a candidate, skipped by `tag:`, and `exec`, `check_host` and `ssh_command` treat it as not found. Its Tailscale node is left out of resolution too, so its Tailscale name or IP does not find it. A node is the denied host's when the host is linked to it, or one of the host's addresses is one of the node's IPs or its MagicDNS name (ignoring case and a trailing dot). An address that is the MagicDNS name's first label or the node's host name makes the node the denied host's only when no other node has that name and the host is not linked to another node: two machines can report the same host name, and such a name does not say which one the host is. An allowed host's node with that name stays visible, and so does the denied host's own node if nothing else names it: link the host to it with `hop ts link` to hide it. Set it with `hop edit <host> --agent-access deny`.
- A denied host can still be another host's jump host, and commands through it work. Its name stays hidden: the jump host shows as `(a host hidden from agents)`, and its names and addresses read `<hidden host>` in `ssh_problem`, check steps, errors and ssh's stderr. A name or address an allowed host also has is not hidden. A name is hidden where it stands as a whole host token: a denied `db` reads `<hidden host>` in `db:5432` and `db.` at the end of a sentence, but not inside `db.prod.example`, and `10.0.0.1` is hidden in `10.0.0.1:22` but not inside `10.0.0.10`. A longer name hop does not know the denied host by (an FQDN that is not one of its addresses) is not hidden.
- An answer about a denied name looks like one about a name that does not exist: what you typed, as the target, the user or a tag, is echoed as you typed it, never masked, where hop echoes it and where ssh names your user on its login to the target. Everything else hop says, from the vault, is masked.
- An agent never trusts a host key on first use. `exec` and `run_snippet` refuse a host with no pinned key, or one behind a jump host with none, and say to run `hop trust <host>`. ssh runs with `StrictHostKeyChecking yes` against the pinned keys only, so a changed key blocks the call.
- Every `exec` and `run_snippet` is logged before and after it runs to `$XDG_STATE_HOME/hop/mcp-audit.jsonl` (mode 0600): time, tool, client name, hosts and exit codes, and for each host the `agent_output` policy that applied, how many markers of each kind the agent got, and whether the output was withheld. It never logs output or the values redacted. For `exec` it logs the command the agent sent, as sent: a secret the agent put in the command is in the log, scrubbed of hop's own values and key blocks but not of the vault's secrets or the well-known formats. For `run_snippet` it logs the snippet's name and the names of the parameters, never their values. Every string is scrubbed as answers are, and control characters are written as escapes. If the log cannot be written, nothing runs.
- `hop mcp --tag work` (repeatable) shows the agent only the hosts that carry at least one of the tags, ignoring case, in every tool: `list_hosts`, `resolve_host`, `check_host`, `ssh_command`, `exec` and `run_snippet`, `tag:` selectors included. It narrows `agent_access`, and a host `agent_access` denies stays hidden whatever its tags. A host outside the tags is hidden exactly as a denied one is: it is left out of lists and candidates, a name or address that matches it answers as one that does not exist, and, as a jump host, it reads `(a host hidden from agents)` and `<hidden host>`. A tag no host carries leaves the agent no host. Use it to organize ("work" and "personal", or one client's hosts per agent); it is not a security boundary against a local attacker, for the reason below.
- `hop mcp --read-only` offers no tool that runs a command: no `exec`, no `run_snippet`, and `check_host` skips its login step.
- The hop auth secrets (`HOP_PASSWORD` and the others) and `HOP_DEVICE_PASSPHRASE` are removed from the server's environment, from ssh's, and from a daemon the server starts.

**Known limits.** Redaction is best effort. The master password passes, since no part of hop holds it once the vault is open. So can a secret in an encoding or format hop does not recognise (base64 of a password, say, or under `redacted` a token format not on the list), a secret split across lines, and a secret that ssh's own limit on the length of a log line has already cut short. Only `agent_output: none` guarantees that no remote text reaches the agent: use it for a host whose output an agent should not read, and do not run commands that print secrets.

`agent_access: deny` and `hop mcp --tag` are guardrails for well-behaved agents, not a security boundary. An agent runs as you and can use your agent socket and unlocked daemon directly. For a real boundary, run the agent in a container or VM.

## Running hop-server

The `Dockerfile` describes the deployment: the image runs `hop-server serve` behind a TLS proxy, with its database in the `/data` volume. Every other `hop-server` command opens that database file directly, while `serve` keeps running:

```
docker exec -it hop hop-server accounts ls --data /data
```

There is no admin API. An admin is whoever can write the data directory, and the commands are local to the server host.

| Command | What it does |
| --- | --- |
| `invite EMAIL [--ttl 7d]` | Issues a single-use registration code bound to the email and prints it, alone, on stdout. Only a hash of the code is stored, so it is never shown again. |
| `invites ls [--all]` | Lists pending invites: ID, email, created, expires. `--all` adds used and expired ones, with the account a used invite created. |
| `invites revoke INVITE\|EMAIL` | Ends a pending invite, given its ID (at least 8 digits of it) or an email (every pending invite for it). The running server sees it at once: the code gets the same answer as a wrong one. A used invite cannot be revoked; it stays for the signup acknowledgment. |
| `invites reissue EMAIL [--ttl 7d]` | Revokes the email's pending invites and issues a new code, in one transaction. |
| `accounts ls` | Every account: email, ID, created, storage used and quota, recovery reserve state, active and total devices, last seen, the vault's head seq and last checkpoint. |
| `accounts show ACCOUNT_ID\|EMAIL` | One account in detail. Its devices, each with its name, `active`, `retired` or `revoked` (and at which seq), the seq that added it, last seen and live sessions. Also live sessions, outstanding login tokens, open enrollments and pending invites for its email. |
| `accounts disable ACCOUNT_ID\|EMAIL [--reason TEXT]` | Disables the account: ends its sessions and login tokens, and refuses it new sessions, logins and recoveries from then on. Its devices lock (below). Nothing is deleted. Disabling a disabled account replaces its reason. `accounts ls --disabled` lists the disabled ones. |
| `accounts enable ACCOUNT_ID\|EMAIL` | Ends a disable. Devices get sessions again and unlock at their next retry; no new login, no new Emergency Kit. |
| `devices block ACCOUNT_ID\|EMAIL DEVICE_ID...\|--all [--reason TEXT]` | Blocks devices of the account (each given by ID or at least 8 of its hex digits; `--all` is every active one): ends their sessions and refuses them new ones. The account's other devices keep working. |
| `devices unblock ACCOUNT_ID\|EMAIL DEVICE_ID...\|--all` | Ends blocks. |
| `sessions revoke ACCOUNT_ID\|EMAIL [--device DEVICE_ID]` | Deletes sessions (and, for the whole account, login tokens). This signs nobody out: each active device signs a new challenge and goes on. It is for a session token that may have leaked. |
| `quota ACCOUNT_ID\|EMAIL SIZE` | Sets the account's storage quota (`512MiB`, `2GiB`, ...). A quota that frees the whole recovery reserve also ends a capacity-exhausted state. |
| `audit [--account A] [--since T]` | Reads the audit trail, oldest first. `--since` takes `7d`, `36h`, `2026-10-01` or an RFC 3339 time. |
| `backup PATH` | Writes a consistent copy of the whole database to a new file. |

Every command takes `--data DIR`; the listing commands take `--json` too. `invites revoke`, `invites reissue`, `accounts disable` and `enable`, `devices block` and `unblock`, and `sessions revoke` show what they will change and ask on a terminal (`docker exec -it`); with `--json` they show it on stderr, so stdout holds only the result. Without a terminal they refuse unless `--yes` is given, and `--dry-run` shows the change and makes none. If the account or the invites changed between what was shown and the change, they refuse with `changed` and change nothing. `invite` and `quota` change state without asking, as before.

**Disabling an account or blocking a device** is the operator's way to stop a device, and the closest thing to "sign out everywhere" a server can do. Both are reversible access controls, not revocations: the server stops serving the device and says why, and that is all. It cannot make a device wipe itself. Only the account can, by revoking the device from another one (`hop auth devices revoke`), since a server that could wipe devices could destroy data.

- *How fast.* The command deletes the sessions at once, but it runs in its own process and can't wake a long-poll, which notices at its next timeout: an online device learns of it within about a minute. A response already on its way may still arrive; it holds nothing the device could not read already.
- *What a device sees.* The server answers `403` with the code `account_disabled` or `device_blocked`, and the reason if one was given, only to a caller that proved it holds the device's key or the account's password: a wrong password or an unknown device still gets the same `401` as before. A device with the current `hop` locks its vault in memory, empties its agent, ends the ssh sessions hop started (as a revocation does), and `hop status` says "locked: the server says its operator disabled this account. The operator's message: ..." with the reason escaped. Nothing is recorded on the device or deleted. Logins (`hop auth login`) and recoveries for the account are refused too, after the password or Recovery Key matched.
- *Undoing it.* After `accounts enable` or `devices unblock`, the daemon asks again within about 30 seconds and unlocks. On a device whose key is a file sealed with a device passphrase, a daemon started as a service has no passphrase to ask with, so run `hop unlock`.
- *Offline devices.* A device that can't reach the server doesn't learn of it, and keeps working offline within the account's max-offline policy (`hop auth policy --max-offline`), as for a revocation. This is deliberate: hop works offline, and the lock is the server's word, not the account's. An unreachable server never clears a lock the device already has, but the lock is held in memory only: a daemon that restarts while the server can't be reached loads the keys, and locks again the next time it reaches the server. An operator who needs a device to stop offline too should ask the account owner to set a short max-offline policy beforehand; nothing the server does reaches a device it can't talk to.
- *Logging out* while disabled or blocked works: retire-status and retire-post stay open to a device that signs, so `hop auth logout` finishes if the device's copy of the vault is up to date with the server's; otherwise it stays pending (`hop auth logout --local-only` gives up on it).
- *Signing in again.* A blocked device can't sign itself back in: unblock it, or log it out and sign in as a new device. A disabled account can't sign in at all until it is enabled.
- *What a block does not do.* It doesn't keep the password holder from signing in as a new device; only disable does. For a lost or stolen device, the owner runs `hop auth devices revoke` and `hop key rotate --all`. `devices block --all` is not "make everyone sign in again".
- *Older clients.* A `hop` from before this change that is already running keeps its keys loaded after a disable or block, and only backs off its sync, until it restarts or someone runs `hop unlock`; at that point it asks the server before any key loads, is refused, and locks. hop is not released yet, so no compatibility mode is kept: update every device. An older client shows the refusal as a plain `403`. An older server never sends these codes.

**Audit trail.** `invite`, `quota`, `invites revoke`, `invites reissue`, `accounts disable` and `enable`, `devices block` and `unblock`, and `sessions revoke` each write one row to the `admin_audit` table: the time, the OS user running the command (`nonroot (uid 65532)` inside the image, whoever ran `docker exec`), the action, the account, the arguments and the result. The row is written in the transaction that makes the change, so a change and its record commit together. A change that fails after it was confirmed is recorded with its error code. No row holds an invite code, and `invites revoke` records an invite by its 12-digit ID however many digits it was given. The command also prints the row to stderr as one JSON line. Under `docker exec` that line stays in the exec session's output; `docker logs` does not see it. Read-only commands write nothing. The trail is accountability among honest operators, not a tamper-proof log: anyone with the data directory can edit it, or restore an older database file.

**Untrusted text.** Emails and device names come from users and devices. In human output, control characters, invalid UTF-8, bidi overrides and other Unicode format characters are printed as `\xNN` or `\uNNNN` escapes, so a name cannot recolour, clear or reorder the terminal. `--json` keeps valid Unicode exact, with the same characters as JSON `\u` escapes; invalid UTF-8 becomes U+FFFD.

**Upgrading.** Database schema version 3 adds the `admin_audit` table. The first time a newer `hop-server` opens a version 2 database, whether to serve or to run any command, it adds the table and records version 3. No existing row changes. Version 4 adds the `account_admin` and `device_blocks` tables the same way, from version 2 or 3. A `hop-server` from before that refuses the upgraded database, so take a backup with the old binary before upgrading if you may need to go back. A database from a newer server is refused and left as it was.

## Checks

Checks run on Kiln, not on the orchestrator:

```
kiln checks run            # go vet, go test, gofmt -l
kiln checks run test       # one check
```

`test` also runs the packages that only exist under `-tags hopdev` (the dev store and the real `hop` binary starting its own daemon).

`scripts/check.sh` defines each check. The ssh integration test needs an `ssh` binary and a passwd entry for the current uid; `scripts/with-passwd.sh` supplies the entry on Kiln. With `HOPKEY_REQUIRE_SSH=1` the test fails instead of skipping when `ssh` is missing.

## End-to-end tests on Kiln

`scripts/e2e/run.sh` runs the whole product on real machines. It builds `hop` and `hop-server` from the worktree with `kiln checks run`, leases two Ubuntu VMs (CLI-A, CLI-B), creates three sandboxes as SSH targets (T1-T3), runs the phases, writes a report and releases everything, also on failure. Nothing from the repository runs on the orchestrator.

Prerequisites:

- the `kiln` CLI, logged in;
- for phases 3-6, a Tailscale auth key that is reusable, ephemeral and tagged `tag:hoptest`, in a file (default `~/hopkey-test/ts-authkey`, or `HOP_E2E_TS_AUTHKEY_FILE`). The tailnet policy must let `tag:hoptest` reach `tag:hoptest`, for example `{"action":"accept","src":["tag:hoptest"],"dst":["tag:hoptest:*"]}`. The script copies the file only by path. Each machine deletes it when `tailscale up` ends, whatever the outcome. The driver deletes it again at cleanup on every machine that got a copy, also with `--keep`, and checks that it is gone.

```
scripts/e2e/run.sh                    # all phases
scripts/e2e/run.sh --phases 1,2       # local only and MCP; no Tailscale key needed
scripts/e2e/run.sh --keep             # leave the machines up and print their IDs
scripts/e2e/run.sh --phases 6 --source ../other-worktree   # build hop from another worktree
```

`--source <dir>` builds `hop` and `hop-server` from another checkout (a branch in review, say) and runs this checkout's suite against them. The report names that checkout's branch, commit and uncommitted files.

The run's kiln identity (`kiln whoami`) is printed and kept in the ledger before anything is allocated, and the report names it. `HOP_E2E_EXPECT_IDENTITY=<name or principal ID>` refuses to run under any other. Without it, the run warns when kiln sees a plain shell but the environment is an agent's, or the reverse. An agent should start a run from its own tool call (the tool's background mode), not with a plain `&`: a process that outlives the call runs as the user's identity, and the agent can then neither see nor release its machines.

The phases:

1. Local use with no account, on both VMs.
2. MCP.
3. Sync, through a throwaway `hop-server` on CLI-A that is reachable only on the tailnet, with a CA made for the run. A description both devices edit is not held, the later push (B's) wins, and B names the item and the field, never either value, in the text of `hop status`, in `hop sync` and in its `daemon.log`.
4. SSH over Tailscale, including a jump host.
5. The revocation matrix, and what revocation does on the device: an online revoke leaves `hop unlock` refused and the agent empty, a proven revocation wipes the vault, `device.key` and `~/.ssh/hop` but keeps `revocation.json`, a device revoked offline keeps working while offline with the policy off (documented, so asserted as working), is cut off within 120 s after it reconnects and stays cut off across a restart, and the account's `--max-offline 1m` policy locks a device blocked from the server and never an idle healthy one (`rev2-*` checks). MCP access counts as working when `list_hosts` lists a host or `exec` ran on T1, whatever else `hop mcp` did. It counts as denied only on one of hop's own refusals (revoked, locked, offline too long, no vault), given in answer to both tool calls, or by a `hop mcp` that exits with one before answering any tool call. "No vault" counts only when the same step sees the proven revocation's wipe of that store (no vault, no `device.key`, a `revocation.json`); a store that is merely empty does not. Any other answer, or a `hop mcp` that hangs or exits, is a harness failure, as is an agent probe that gives no clear answer.
6. `hop key rotate` against real sshd: the sandboxes' stock Ubuntu sshd (StrictModes on), T2's jump-host target and CLI-B's sshd. `--dry-run` changes nothing; rotated hosts keep every other `authorized_keys` line byte for byte and the old line's options (`restrict` and `from=`, which sshd then enforces on the new key); the old key is refused; T3, whose sshd is set to take only the lines it had before (`AuthorizedKeysCommand` on a snapshot, with a hook that logs each offered key's fingerprint and whether the live file holds it), refuses the new key and is put back, and the hook log proves the new key was installed and refused before the restore; a second record of a rotated account is `already-rotated`; B follows with nothing done there; lines appended on T1 during a rotation are kept, each exactly once, and the T1 clock is measured against A's so at least one append is shown to land inside the rotation (none is a harness failure, as are zero appends); the rotation must reach its edit, so it either ends `rotated` (`old_key_removed`) or fails on hop's own conflict check (`~/.ssh/authorized_keys changed while hop was editing it`) with the host `unchanged`, and any other failure fails the check (`rot-*` checks). T3's sshd is put back to stock and checked, also when the phase stops early: `sshd -T` must succeed and show deploy the same `AuthorizedKeysFile` and `AuthorizedKeysCommand` (`none`) as the stock config did at setup. A build without `hop key rotate` (exit 255, `unknown key subcommand "rotate"`) records a skip; a detection that gets any other answer is a harness failure. The same goes for `hop auth policy`.

Every check is one JSON line in `e2e-out/<run-id>/results.jsonl`. `REPORT.md` next to it has a table per phase and the failures in detail. Assertions encode the intended behaviour, so known product gaps show up as FAIL, tagged with their bug ID. Where the product README documents a limit (two changes to one unit of fields are held, secrets hop does not know pass through MCP output, open sessions survive a revoke), the check asserts the documented behaviour: status `limit` means it holds as documented, and the report lists it under Documented limits with the README reference. A limit never counts as a failure and never changes the exit code; behaviour that differs from the documentation is a FAIL. A check whose prerequisite did not hold (a session that never connected, a daemon that never started, an answer that was not valid JSON, a firewall block that did not take effect) fails as `harness`; it never passes. A full run takes about 20 minutes: about 6 to build, lease and set up the machines, then about 14 for the phases. Phases 1-2 alone should take under 10 minutes.

The exit code is the verdict:

| Exit | Meaning |
| --- | --- |
| 0 | every check passed |
| 1 | assertion failures (known product bugs show up here) |
| 2 | harness failures: setup, a `harness` check, log collection or masking, or a machine that could not be released |
| 3 | missing coverage: a selected phase that did not run to its end, a step that did not finish with exit 0, or a machine that reported no checks |
| 128+n | interrupted by signal n, whatever the verdict; `REPORT.md` notes the signal, and its verdict covers only what ran |

A run ID is used once: the run's directory is reserved with a plain `mkdir`, so a repeated `--run-id` is refused before it can touch another run's ledger.

Cleanup runs on every exit, including Ctrl-C. Each allocation runs in a worker of its own under `setsid` (`scripts/e2e/alloc.sh`), which ignores INT, TERM and HUP and writes the operation ID and the machine ID to `alloc/<kind>.<who>.rec` the moment kiln returns them, so a signal to the run's whole process group cannot lose one. Cleanup waits for those workers, asks kiln about any operation still without a machine, and reports one it cannot resolve as a harness failure that names the operation. It then releases everything this run asked for and checks with `kiln vm list` and `kiln sandbox list` that it is gone. Each of these outcomes (auth key deleted, each release, the final check) is a phase 0 check in the results, and `REPORT.md` is written after them, so a release that failed shows up in the saved report. A second Ctrl-C only skips the rest of the log collection; the releases still run. Logs leave a machine only after its suite jobs are stopped and each file is masked into a separate export directory. A file that cannot be masked is withheld and counted as a harness failure. Cross-machine timings are corrected by the A-B clock offset, measured over the tailnet at the start and the end; an offset over 0.5 s is a harness failure.

`--reuse e2e-out/<run>` (with machines kept by `--keep`) is for debugging. Each machine has a lock file (`$TMPDIR/hk-e2e-locks-<uid>/<id>.lock`, held with `flock` for the whole run), so two runs never share machines; a ledger whose machines were released (`machines.released`) or are no longer live is refused. It stops every job of the earlier run (they all run in `hke2e.slice`), removes only the firewall rules the suite added (tagged `hk-e2e`), and clears the completion markers, which carry the run ID.
